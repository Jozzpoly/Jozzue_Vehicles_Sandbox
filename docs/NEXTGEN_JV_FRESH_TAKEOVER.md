## 9. Visual Model / Rig Forensics — first-class problem

Do not reduce this phase to "inspect old rig code".

Reconstruct the following layers separately.

### Asset truth

Establish only what evidence supports about:

- hierarchy;
- origins/pivots;
- local axes/handedness;
- scale;
- parentage;
- node/part identity;
- mesh geometry.

### Import truth

Trace relevant:

- coordinate conversion;
- axis swaps;
- scaling/mirroring;
- baked transforms;
- reparenting;
- runtime normalization.

### Visual-runtime truth

Observe/trace:

- position/rotation/scale authority;
- which visible members follow bodies;
- which are procedurally drawn between endpoints;
- which are decorative or derived;
- actual visible pivots and motion.

### Physics truth

Separately establish:

- bodies;
- joints;
- anchors;
- axes;
- hardpoints;
- constraints;
- steering/suspension/driveline causal authority.

### Correspondence

Only after the layers above are partially recovered should the project assert whether a visible point/part corresponds to a physical body/joint/anchor.

Names, proximity and apparent motion are insufficient by themselves.

### Phase B — minimal JV_CORE source orientation

Before broad documentation reading:

- map repository topology;
- locate runtime entry points;
- locate likely vehicle construction, physics, visual/import and asset paths;
- read only the minimum source required to launch and frame the forensic questions.

Do not yet build an architecture interpretation.

### Phase C — rendered forensic observation

Use **Sol Max + computer-use/browser** when local rendered/spatial evidence is materially useful.

The first Max pass should be observational rather than explanatory. It should record what is actually visible and moving without assuming visual=physics.

Useful observations include:

- real motion paths;
- apparent pivots;
- which parts move together;
- which parts stretch/reorient;
- obvious offsets, mirrored relationships or implausible axes;
- behavior under steering/suspension/load if safely observable.

Record observations separately from interpretations.

### Phase D — runtime/source tracing

Choose a small number of high-information observed relationships and trace them back through:

`rendered part → visual transform/import → authored/derived endpoint → physical body/joint/anchor`

Do not try to reverse engineer the entire vehicle at once.

### Phase E — early Owner correction checkpoint

Present the Owner with a compact falsifiable reconstruction, for example:

- A appears physically causal;
- B appears visual-only;
- C may be an import/transform defect;
- D remains unknown.

Ask the Owner to correct/falsify those specific claims rather than asking for a full history lecture or code navigation.

If the reconstruction is substantially wrong, change the method rather than rationalizing around the error.

### Phase F — donor extraction

Classify recovered fragments as:

- useful donor capital;
- negative evidence / known bad approach;
- unresolved/UNKNOWN.

Prefer extracting small principles/mechanisms rather than adopting old systems.

### Phase G — fresh representative-problem selection #2

Only now compare materially different construction problems on:

- information gain;
- product representativeness;
- adaptation/intent semantics;
- causal consequence;
- real-asset usefulness;
- visual/rig confounds;
- implementation cost;
- causal blast radius;
- prototype gravity.

Then decide whether the next move is another donor check, an experiment design, implementation or Owner judgement.
