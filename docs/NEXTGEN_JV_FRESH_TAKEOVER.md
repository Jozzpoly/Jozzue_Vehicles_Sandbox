## 3. The key problem exposed by Rep4

Rep4 increased **hardpoint bandwidth** but did not materially increase **structural agency**.

The Owner could:

- move several mechanically different points;
- make normal or absurd geometry;
- run the real mechanism;
- return to the authored build.

The Owner still could not:

- create a new meaningful relation;
- delete one;
- reconnect it somewhere else;
- replace one construction strategy with another;
- make a configuration whose topology was not already encoded by the experiment author.

Therefore do not select the next experiment by asking `which additional hardpoint should become editable?`.

The frontier is now **construction grammar / topology interaction**.

## 4. Workflow correction — separate prototype roles

Retain the causal rule:

> **One presented mechanical relation has one authority truth. Physics and visible representation are downstream projections of that same relation.**

Add the post-Rep4 process rule:

> **Do not spend integration-grade validation on an interaction idea before it has earned enough Owner value to justify hardening.**

Use three lanes deliberately:

### Causal / implementation lab

For physics/runtime/authority unknowns. Narrow, rigorous, machine-heavy. No unnecessary UI polish.

### Interaction / experience spikes

For construction grammar, spatial manipulation, recognition and creative breadth. Fast, disposable and preferably comparative. A spike may be non-physical or partially simulated **only when clearly labelled and when no causal claim is being made**.

Require only lightweight machine/browser smoke before Owner comparison.

### Integration specimen

Only after an interaction grammar earns enough Owner evidence and the needed causal seam is worth connecting. Then restore full causal/browser qualification.

This separation is intended to improve both speed and quality: more design alternatives can be explored before the project hardens one local optimum.

## 5. Immediate next program — comparative construction-grammar spikes

Start a new named experimental branch. Do not modify `main` directly.

The goal is not a generic builder architecture. It is a disposable **look-and-feel / role exploration** of direct construction semantics.

Build at least two materially different grammars against the same small scene/context so the Owner can compare them rather than judge one path in isolation.

Strong candidates:

### A — connect-by-drag

- relevant physical connection points become visible on hover/selection;
- drag from one point to another creates an adaptive link;
- dragging an endpoint elsewhere reconnects it;
- removing a link is direct and reversible;
- the visible link immediately follows its endpoints.

### B — component-first placement

- choose one of a very small number of recognizable components;
- place it in the scene;
- manipulate/snap its functional endpoints onto construction points;
- the component adapts to its installation.

### C — hybrid, only if A/B comparison justifies it

- simple links use connect-by-drag;
- semantically rich components such as damper use component-first placement;
- both share one visible connection language.

Do not implement all three merely because they are listed.

## 6. Minimum experiential requirement

A spike is not worth Owner time unless the Owner can make at least one meaningful configuration whose **relation/topology was not already completely pre-authored**.

This is stronger than Rep4's `three hardpoint classes` requirement.

The intended Owner questions are:

- does this feel more like assembling a mechanism than tuning coordinates?
- can I invent a small structural intent of my own?
- can I try, undo/reconnect and pursue another path quickly?
- are meaningful mechanical ideas visible without the tool forcing one recipe?
- which of the competing grammars is worth integrating with real physics?

Do not ask about vehicle feel yet.

## 9. Direct-manipulation principles to target

Support research reinforces existing JV direction:

- objects/relations of interest should stay visible;
- actions should be rapid, incremental and reversible;
- consequence of a construction action should be immediately visible;
- connection points/compatibility should become salient when relevant rather than always covering the scene in debug markers;
- optional snap/grid/gizmo and exact numbers should support direct construction rather than replace it;
- preserve permissiveness: weird construction should usually be possible and diagnosed, not normalized away.

Treat Trailmakers, Besiege, Scrap Mechanic, GearBlocks, Dream Car Builder and CAD systems as inspiration/donors only, never as architecture authority.
